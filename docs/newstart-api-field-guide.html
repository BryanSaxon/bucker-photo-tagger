NewStart API

A read-only catalog API for homebuilding: communities, floorplans, lots, priced options and a 2,136-item product library. This guide is what the collection itself does not contain — schemas, relationships, and the places the data will bite you.

01

Orientation

Everything hangs off a community. Get a project_code from /communities, and every other endpoint you care about is a path underneath it.

The API is entirely read-only — 18 endpoints, all GET, no writes. It is a Ruby on Rails app behind nginx (the saved responses carry x-request-id, x-runtime and a strong ETag).

Two things to know before you read anything else:

  • The source collection has no documentation. No endpoint descriptions, no query parameters, no example values for the path variables, no test scripts. Every schema in this guide was derived by parsing the six saved response examples.
  • Only 6 of the 18 endpoints have a captured response. The other 12 exist as requests that were never run, or whose responses weren't saved. They are marked unverified throughout, and their schemas are inference, not fact. Treat them as a to-do list for your first session against a live token.

All six verified examples were captured against a single community — 1682, Bradbury at Blackridge. Distributions quoted in this guide (row counts, enum frequencies, join integrity) describe that community, and may not generalize.

02

Auth & conventions

Authentication

A single header carrying both a token and an email, in Rails' structured token format:

Authorization: Token token="<api_token>", email="<api_email>"

The quotes are part of the format — don't strip them. Both values are blank in the collection, as is base_url; get all three from the API owner.

Response shape

Every verified response is an object wrapping a single named array — {"lots": [...]}, {"models": [...]}. Only /product_library adds a second key, count.

Numbers are strings

Every money value, quantity and price comes back as a decimal string: "615000.00". Parse with a decimal type, never a float. The single exception in the entire API is Option.add_floor_area, which is a real integer.

There is no pagination

/product_library returns all 2,136 products in one response, and count equals the array length — it is a total, not a page hint. No endpoint accepts limit, offset or page. Since responses carry a strong ETag, cache aggressively and revalidate with If-None-Match rather than trying to fetch less.

Keys are codes

There are no numeric surrogate ids anywhere. Entities are identified by business codes — project_code, product_code, room_code — and models are identified by a display string, model_description. Case and padding matter; see the redlines.

06

Redlines

Seven things in this API will cost your dev an afternoon each if nobody tells them first. This is that telling.

R-0194% of the /models payload is the same array repeated

Each of the 49 models carries a rooms array — and all 49 arrays are byte-identical. It is a global 226-entry room dictionary, duplicated once per model. That's ~630 KB of a 668 KB response; the stored Postman example is 1.49 MB.

A model's actual rooms are in base_model_rooms, a lowercase CSV of about 99 codes. The rooms array is not model-specific and never varies.

Do this — read the dictionary once from models[0].rooms, drop it from the other 48, and resolve base_model_rooms against it. Then go test /models2, which almost certainly exists to fix exactly this.

R-02/options is not the full option catalog

Every one of the 1,347 rows has category = "Drawn Options", spread across just four subcategories: Structural/Plumbing, Windows/Doors/Ceiling, Cabinets, Fireplaces.

Meanwhile /steps for the same community describes 40 categories and 105 subcategories — flooring, lighting, trim, appliances, paint. None of that is in /options.

Do this — don't build a price engine assuming /options is complete. Confirm with the API owner where non-structural selections and their prices come from before you scope the work.

R-03Lots don't reliably resolve to models, and gross_sale doesn't add up

Two separate traps on the same entity. First, Lot.model_description is free-text drifted: 40 of 328 lots are null, and 14 more values have no matching model — including variants like "Addington 1C (basement)".

Second, the pricing does not reconcile. base_model_price + options + lot_premium + lot_price equals gross_sale on only 245 of 328 lots. 67 non-zero lots genuinely disagree (discounts and incentives are not exposed anywhere), and 41 lots — almost all Open — report "0.00" because they're unsold.

Do this — treat gross_sale as authoritative and never recompute it. Match models with a fallback path, and filter gross_sale = "0.00" out of any average-price calculation.

R-04Steps give you names; everything else gives you codes

/steps is the only endpoint that describes the configurator's layout — which is exactly what you need to build a UI. But its categories and subcategories are display names ("Brick & Stone"), while Option and Product carry codes (01Brick). There is no code anywhere in the steps payload.

String matching does not rescue you: only 1 of the 4 option subcategory names appears in the 105-name step vocabulary.

Do this — ask the API owner to add category_code / subcategory_code to /steps. Until then you cannot reliably drive a stepped configurator from this data. This is the single highest-value fix on the list.

R-05Product.image is a flag, and it's misspelled in the data

It looks like a filename. It isn't. The values are sentinels: BookYesImage (1,207 rows), empty (472), BookNoImage (447) — plus typos that are live in the source data: BookNolmage with a lowercase L (2 rows), BookYesIamge (1 row), and 4 rows of an unexplained OB49.

So there is no documented way to get from a product to an actual image name for /product_images/{name}.

Do this — match case-insensitively on a yes/no substring rather than on equality, or those typo rows silently misclassify. Then ask how image names are derived.

R-06Timestamps have lost their trailing zeros

moddatetime and lastmoddatetime are nominally YYYYMMDD.HHMMSS. But the values have been round-tripped through a float somewhere upstream, so trailing zeros are gone — observed lengths are 10, 13, 14 and 15 characters. "20230824.1131" and "20230824.11335" are the same field as "20230824.113138".

Do this — right-pad the fractional part to 6 digits before parsing. Parse naively and you will silently produce wrong times on the 244 rows that are short.

R-07Case, padding and undefined path variables

A cluster of small things that each break a lookup:

  • lot_type contains both Reg (245 rows) and REG (4 rows). Normalize before grouping.
  • lot numbers are zero-padded strings ("0902"). Don't parse to int and back.
  • room_code is uppercase; every reference to it (base_model_rooms, area_associations, room_replacement_rules) is lowercase.
  • Model.base_model_price has one decimal place ("530000.0"); Lot.base_model_price has two ("615000.00"). Normalize before comparing.
  • {model_code} and {image_name} appear in paths but no payload field has either name. For models, try model_description URL-encoded first.
  • Option.description is truncated mid-word at ~250 characters in the source data.
  • Product.attribute1 is a CSV choice-list of up to 55 options, not a single value — and despite the 1, there is no attribute2.

Recipes

Fetch everything for one community

Four calls, all parallel after the first. Expect ~2.5 MB uncompressed.

GET /api/v4/communities                      → pick a project_code

GET /api/v4/communities/1682/models          → 49 models  (strip 48 rooms[])
GET /api/v4/communities/1682/lots            → 328 lots
GET /api/v4/communities/1682/options         → 1,347 options (drawn only)
GET /api/v4/communities/1682/steps           → 48 UI steps
GET /api/v4/product_library                  → 2,136 products (cache hard)

Price a model with its options

options
  .filter(o => o.model_description === "Abigail 1A")
  .map(o => ({
    ...o,
    product: productsByCode.get(o.product_code),   // always resolves
    price:   new Decimal(o.gross_sale)             // string → decimal
  }));

Resolve a model's rooms

// read the dictionary ONCE — it's identical on every model
const roomsByCode = new Map(
  models[0].rooms.map(r => [r.room_code.toLowerCase(), r])
);

const modelRooms = model.base_model_rooms
  .split(",")
  .map(c => c.trim())
  .filter(Boolean)
  .map(c => roomsByCode.get(c))
  .filter(Boolean);          // ~13% won't resolve — expected

Parse a timestamp safely

function parseModDateTime(v) {
  const [date, frac = ""] = v.split(".");
  const t = frac.padEnd(6, "0");                   // R-06: restore lost zeros
  return new Date(Date.UTC(
    +date.slice(0, 4), +date.slice(4, 6) - 1, +date.slice(6, 8),
    +t.slice(0, 2), +t.slice(2, 4), +t.slice(4, 6)
  ));
}

Using the spec

This guide ships with a companion OpenAPI 3.1 spec — newstart-openapi.yaml — covering all 18 operations with full schemas, enums, and every caveat above attached to the field it applies to. It validates clean: no broken references, no duplicate operation ids, every path parameter declared.

Render it as Swagger

  • Swagger UI — paste into editor.swagger.io for the classic interactive page.
  • Redoc — npx @redocly/cli preview-docs newstart-openapi.yaml gives a cleaner three-column read, and renders the long field descriptions better.
  • Back into Postman — import the YAML to regenerate the collection with every description attached, which the current collection lacks entirely.
  • Client generation — npx openapi-typescript newstart-openapi.yaml -o newstart.d.ts for typed responses.

Read the verification flags

Every operation carries x-verified: true|false. Filter on it to see exactly which 6 endpoints are grounded in a real response and which 12 are inference:

yq '.paths.*.get | select(."x-verified" == false) | .operationId' newstart-openapi.yaml

As your dev confirms the unverified endpoints against a live token, flip the flags and paste the real responses in as examples. The spec is designed to be the thing that gets less wrong over time — not a snapshot.
